# 本体论流派与OWL简介

> 「确定性 OWL 派、LLM 自动抽取派、图数据库底座」是挑开源仓库时的实现切法，不是本体论的全部。**OWL** 是 W3C 的 Web Ontology Language（网络本体语言），是知识工程派最常用的形式化语言，不是「本体」的同义词。下文按 W3C OWL / OWL 2、RDF、RDFS、SKOS、SHACL、SPARQL，以及 Gruber、Borst、Uschold / TOVE、Dietz DEMO、BFO / DOLCE / UFO 等线索整理。

## 1. 工具谱系上的三种切法

| 切法 | 实际在分什么 | 典型仓库或产品 |
| --- | --- | --- |
| 确定性 OWL 派 | 人事先写类、属性、公理；推理机按逻辑推出蕴含 | WebVOWL、FIBO、gist、部分 TrustGraph / AWS COA |
| LLM 自动抽取派 | 从文档或表结构归纳术语和关系，再给人审 | EvoOntology、NVIDIA Auto Ontology、Semantica 的生成器、不少 GraphRAG |
| 图数据库底座 | 节点和边先存起来，本体可有可无 | Neo4j、各类「知识图谱」产品 |

三者可以叠：OWL 文件可以进图库；LLM 可以起草 OWL；图库可以完全不跑描述逻辑。所以这是**工具谱系**，不是互斥学派。

选型时至少再加一刀：**有没有动作、写回和权限**。有无这一项，比「是不是 OWL」更能区分 Palantir 路线和纯 OWL 仓库。

## 2. 本体在工程里的含义

哲学里 ontology 研究「有什么种类的存在」。计算机里被 Gruber（1993）收成工程定义：对概念体系的显式规定；Borst 补上「共享、形式化」。

企业场景里，本体要回答的是：承认哪些对象、如何识别、彼此如何关联、当前什么状态、必须满足什么规则、谁可以发起什么动作。它是共享业务坐标系，不是把所有数据搬到一处。

一组常用对照：

| 概念 | 含义 |
| --- | --- |
| Taxonomy | 树。只说「是一种 / 属于」 |
| Ontology | 图 + 约束；现代产品里往往还有动词 |
| Knowledge Graph | 本体被实例化后的事实网络。本体相对稳定，图谱持续增长 |
| TBox | 术语盒：类、属性、公理 |
| ABox | 断言盒：某个体属于某类、某两个体有某关系 |
| OWL | W3C 形式化知识表达语言，适合交换和逻辑推理 |
| Palantir Ontology | 以对象、属性、链接、动作为核心的企业运行契约 |

实务上常把「本体」偏 TBox、「知识图谱」偏 ABox。很多产品把图谱叫本体，其实只有实例层，关系类型稀、没有公理。

## 3. 九条常见脉络

不止三种。下面几条经常同时存在，讨论时最好先标明站在哪一条上。

### 3.1 哲学 / 上层本体

先规定世界里最抽象的类别：物、过程、角色、时间、空间，再往下挂领域。

代表：BFO（ISO 21838-2）、DOLCE、UFO、CCO。工业上 IOF 挂在 BFO 下。这一派在乎分类不打架（人是物还是角色），不直接管订单怎么改。

### 3.2 知识工程 / 描述逻辑派

把共享词汇写成可推理的公理。爱丁堡 Enterprise Ontology、多伦多 TOVE、METHONTOLOGY 都在这里。产出是词汇表加公理，今天多半落成 RDF + OWL。评价手段是 competency questions：本体必须能回答哪些问题，就建到多深。

金融 FIBO、极简上层 gist 是这一派的内容库；HermiT、ELK 是推理机；WebVOWL 是看图工具。OWL 最常待在这里。

### 3.3 企业工程派（DEMO）

Dietz 的 Enterprise Ontology：把**组织本质**和**实现方式**分开。B / I / D 三层（业务沟通、信息处理、文档与数据），交易模式是请求 → 承诺 → 执行 → 声明 → 接受。产出是协作、过程、动作、事实模型，通常不是 OWL 文件。关心「企业靠什么沟通在创造事实」，较少对应到三元组库。

### 3.4 概念建模派

用 UML 味道的语言建本体（OntoUML、UFO 加 UML profile）。和 OWL 可互译，但读者是业务建模者，不是逻辑学家。

### 3.5 受控词表 / 轻量语义

只做「是一种 / 同义 / 上位」，几乎不做复杂约束。图书馆、主数据编码、搜索同义词常用。SKOS 不是 OWL 的简化替代，是另一档：词表，不是公理系统。

### 3.6 运行时语义层

对象、属性、链接、动作、权限一体。本体是生产契约：大模型只能调工具，工具在权限里写回。Palantir Foundry Ontology、用友 YonOnto、Ontexus 走这条。和 OWL 可以导出对接，但核心不是描述逻辑。

### 3.7 数据 / 指标语义层

术语对应哪张表、哪个指标用哪条 SQL。问的是「数怎么算」，不是「世界里有哪些类」。问数产品的术语加示例 SQL、NVIDIA Auto Ontology 的 Term / SQL attribute 属于这里。它可以长得很像本体，职责仍是问数。

### 3.8 知识图谱作为实例层

图谱存已经发生的事实。图数据库是底座，不是流派。没有 TBox 时，节点和边只是带类型的存储。

### 3.9 LLM 抽取是建造方法，不是独立本体论

从文本抽三元组、从 schema 归纳类，解决的是第一稿从哪来。审定之前它不是共享概念体系，只是候选。TrustGraph 用 OWL 约束抽取，Auto Ontology 用人认证 SQL 属性，都是「抽取 + 某派契约」的组合。

## 4. OWL 的定位与构件

**OWL = Web Ontology Language**，W3C 的网络本体语言。缩写故意写成 OWL 而不是 WOL：好念，也呼应猫头鹰（智慧的传统象征）。中文常称「网络本体语言」，或直接说 OWL。

它要解决的问题：词汇不能只靠自然语言或 XML 标签。要让机器知道，例如：

- 「合同」是一类事物
- 「甲方」是合同指向组织的关系
- 「框架协议」是合同的子类
- 一份合同不能同时是「已作废」和「履行中」（若写下互斥公理）
- 从「甲是乙的子公司、乙是丙的子公司」能否推出甲与丙的关系（若写了传递性）

OWL 建在 **RDF**（资源描述框架，主谓宾三元组）和 **RDFS**（类、子类、属性）之上，把表达能力加到描述逻辑（Description Logic）能推理的程度。祖先是 DAML+OIL。**OWL 1** 于 2004 年成为 W3C 推荐标准；**OWL 2** 于 2009 年发布。现在说的 OWL 多半是 OWL 2。

### 4.1 它写什么

| 构件 | 例子 |
| --- | --- |
| 类（Class） | 合同、人员、项目 |
| 个体（Individual） | 某一份具体合同（已靠近 ABox） |
| 对象属性 / 数据属性 | 负责人（连到人）、金额（连到数字） |
| 公理 | 子类、等价、不相交；属性的定义域 / 值域、传递、对称、函数性 |
| 约束 | `someValuesFrom`（至少有一个合格值）、`allValuesFrom`（所有值都必须是）、基数（恰好 1 个甲方） |

TBox 是这类约定；ABox 是断言。OWL 文件两者都能写，工程上往往 TBox 用 OWL，实例用图库或表。

### 4.2 开放世界与封闭世界

这是 OWL 和企业数据库最容易撞车的一点。

- 数据库 / SQL：**封闭世界**。表里没有，就当假。
- OWL：**开放世界**。没写不等于假，只是未知。没有「作废」三元组，推不出「没作废」。

所以「用 OWL 当主数据约束」经常让业务落空：以为写了互斥就能挡脏数据，推理机却说「我不知道」。要在图上做「形状校验」（这条边必须有、这个字段必须是 IRI），现在更常用 **SHACL**（Shapes Constraint Language）。OWL 偏推出新知，SHACL 偏检查是否符合形状。

### 4.3 OWL 2 的档位

完整 OWL 2 DL 推理可能很贵。W3C 切了几个可计算的剖面：

| 剖面 | 大致用途 |
| --- | --- |
| OWL 2 EL | 超大分类体系（如 SNOMED 医学术语） |
| OWL 2 QL | 本体当查询重写，底下仍是关系数据库 |
| OWL 2 RL | 用规则引擎做可扩展推理 |
| OWL 2 DL | 标准描述逻辑，有推理机 |
| OWL 2 Full | 和 RDF 完全兼容，推理不保证可判定 |

企业项目若号称「上了 OWL」，要问清是 DL、EL，还是只把 `owl:Class` 当标签用。后一种和电子表格里的类名差别不大。

### 4.4 和邻近标准怎么排

| 名字 | 角色 |
| --- | --- |
| RDF | 图的数据模型：三元组 |
| RDFS | 很浅的类和属性 |
| **OWL** | 类、属性、公理、可推理 |
| SKOS | 概念方案、上下位、备选标签，给词表 |
| SHACL | 图的形状约束，给校验 |
| SPARQL | 图查询语言 |
| PROV-O | 溯源（谁、何时、从哪来） |

Semantica、TrustGraph、AWS COA 把 OWL / SHACL / SKOS 捆在一起，是因为：分类用 OWL，校验用 SHACL，同义词用 SKOS，查询用 SPARQL。

### 4.5 企业运行时较少直接用 OWL 的原因

- 业务专家写不了描述逻辑；写得动的人维护不起开放世界语义。
- 推理机对「今天订单状态」这种高频读写不友好。
- OWL **没有「动作」**：不能表达谁可以在什么条件下改状态、如何写回源系统。Palantir 的 Action、问数产品的示例 SQL、Agent 的工具清单，都不在 OWL 核心里。
- 交换和归档仍然适合 OWL：FIBO、行业互操作、监管要可机读定义时，导出 OWL 有价值。

OWL 是一种形式化语言，特长是共享分类和逻辑蕴含；不是本体论的同义词，也不是企业落地的唯一载体。

## 5. 选型时如何对照这些脉络

不必先站队「只做 OWL」或「只做抽取」。更稳的问法是：

1. **契约写在哪**：公理（OWL）、对象—动作（运行时）、术语—SQL（问数）、词表（SKOS）？
2. **实例存在哪**：三元组库、属性图，还是根本不物化、用时从源系统算？
3. **第一稿谁写**：人、从 schema 编译，还是从文档抽取？审定门在哪？
4. **要不要改世界**：只要查询，还是必须有权限动作？

GitHub 上那三派回答的是第 2、3 问。第 1、4 问要回到 DEMO、Palantir 运行时和指标语义层，否则会把 WebVOWL、Neo4j 和 Auto Ontology 当成同一类产品比星标。

## 6. 小结

| 要点 | 结论 |
| --- | --- |
| 三种切法 | 工具谱系，不是互斥学派；还要看有没有动作、写回和权限 |
| 本体 | 共享概念体系（偏 TBox）；图谱是实例化后的事实网络（偏 ABox） |
| OWL | W3C 网络本体语言，建在 RDF / RDFS 上，擅长分类与逻辑蕴含 |
| 开放世界 | 没写不等于假；形状校验更常用 SHACL |
| 企业运行时 | 对象—动作—权限往往不在 OWL 核心里；OWL 仍适合交换和归档 |

# 自动化开发工作流仓库调研

> 本文整理两类和「本地自动化开发」有关的 GitHub 仓库：一类是把需求、改代码、跑命令、修失败串起来的编程代理；一类是用 `SKILL.md` 规定做法、交给已有代理去执行的技能与流程工具。它们都不是某一门语言的框架。星标取自 2026-10-19 检索，之后会变。

## 1. 定义

这里的自动化开发，指代理在本机仓库里连续做完几件事：读需求、改代码、执行命令、看测试失败、再改，并把设计、任务和验证结果留在磁盘上。下一轮不靠上一轮聊天记录，靠仓库里的文件接着做。

**结论性定义：** 高星仓库分成两条路。编程代理自己带运行时、终端和面板，负责「谁来干」。技能仓库只提供 `SKILL.md` 和流程模板，负责「按什么规矩干」，调度仍要交给 Claude Code、Codex、OpenHands 或同类宿主。

## 2. 覆盖范围

| 对照 | 本文所指 |
| --- | --- |
| 全天无人值守闭环 | 仓库提供一轮里的步骤和落盘格式。定时触发、单次超时、电脑是否开着，属于宿主。 |
| 星标与全流程 | 按是否自带运行时、是否规定步骤来选型。OpenCode、Claude Code、Codex 主界面仍是终端编码代理；MetaGPT、Spec Kit 更靠近从需求写到实现。 |
| 技能目录 | `awesome-claude-skills`、`awesome-openclaw-skills` 是链接清单，安装后仍要另选代理和流程模板。 |

## 3. 编程代理

挑选标准是：不绑一种语言、能执行多条命令、能从实现走到测试和返修、最好有面板。下面按和这套标准的接近程度排列，不是按星标。

| 仓库 | 约略星标 | 界面 | 和全流程的关系 |
| --- | --- | --- | --- |
| [OpenHands/OpenHands](https://github.com/OpenHands/OpenHands) | 9.1 万 | 本地 Web 面板 Agent Canvas，可再挂命令行 | 最接近控制台。能改文件、跑 shell、看 diff。可通过 Agent Client Protocol 拉起 Claude Code、Codex、Gemini CLI、Pi、OpenCode。定时任务每轮默认约 10 分钟，文档上限约 30 分钟，下一轮不继承上一轮对话。 |
| [FoundationAgents/MetaGPT](https://github.com/FoundationAgents/MetaGPT) | 7.1 万 | 命令行，文档产出为主 | 一句话需求拆成用户故事、竞品、数据结构、接口和代码。角色是产品、架构、工程。真实测试循环弱于 OpenHands。 |
| [cline/cline](https://github.com/cline/cline) | 7.0 万 | VS Code / JetBrains，另有 headless CLI | Plan 先对齐方案，Act 再改代码、跑终端、看报错。每步 diff 可先给人看。 |
| [block/goose](https://github.com/block/goose) | 5.5 万 | 桌面应用 + CLI | 本机改代码、跑命令。单会话可开子代理。没有内置的需求到修 bug 状态机。 |
| [OpenBMB/ChatDev](https://github.com/OpenBMB/ChatDev) | 3.5 万 | Web 流程画布 | 1.0 是虚拟软件公司：设计、编码、测试、文档。2.0 变成通用多智能体编排。 |
| [Aider-AI/aider](https://github.com/Aider-AI/aider) | 5.0 万 | 终端 | 结对改代码并自动提交。测试要人在对话里要求。 |
| [plandex-ai/plandex](https://github.com/plandex-ai/plandex) | 1.6 万 | 终端 | 计划、改很多文件、执行命令、排错。改动先留在 diff 沙箱。 |
| [princeton-nlp/SWE-agent](https://github.com/princeton-nlp/SWE-agent) | 2.1 万 | 研究用 CLI | 对着已有 bug 和失败测试做修复，不是日常控制台。 |
| [Pythagora-io/gpt-pilot](https://github.com/Pythagora-io/gpt-pilot) | 3.4 万 | 角色流水线 | 从规格写到调试。仓库已停止维护。 |

同一时期星标更高、但不承担整条流水线的还有 [anomalyco/opencode](https://github.com/anomalyco/opencode)（约 21 万，终端编码代理，桌面版当时仍是 beta）、Claude Code（约 15 万）和 Codex CLI（约 13 万）。OpenHands 的价值是把这些命令行收进同一个面板，而不是替换它们的模型。

OpenHands 不必放进沙箱。`npm` 安装后，代理以当前用户身份跑在本机，面板里用 Open Workspace 指定仓库目录。Docker 只挂载需要的目录，才是沙箱。指定了工作区之后，无沙箱模式下进程权限仍是当前用户，命令可以访问该用户能访问的其他路径。

## 4. OpenHands

仓库：[OpenHands/OpenHands](https://github.com/OpenHands/OpenHands)（MIT，当日约 9.1 万星）。当前对外的产品名是 Agent Canvas：一个自托管的开发控制台，用来发起对话、看文件和终端，并按时间或事件跑自动化。默认跑在本机，也可以把执行放到 Docker、虚拟机或 OpenHands Cloud。面板地址是 [openhands.dev](https://openhands.dev)，文档在 [docs.openhands.dev](https://docs.openhands.dev/openhands/usage/agent-canvas/setup)。

它自己带一个 OpenHands 代理，也能通过 Agent Client Protocol 改用 Claude Code、Codex、Gemini CLI、Pi、OpenCode，或任何实现了该协议的命令行。模型在 Settings → LLM 里配置，可以用供应商密钥，也可以接本机的 OpenAI 兼容服务。

| 功能 | 做什么 |
| --- | --- |
| 工作区 | 对话开始前用 Open Workspace 指定本机目录。代理在这个目录里读写文件、执行命令。 |
| 多代理 | 新对话前选择 Agent Profile。一轮开始后不能换成另一个命令行，只能换该命令行自己的模型。 |
| 自动化 | Automate 里按日程或事件创建任务。每轮是一次新对话，默认约 10 分钟，文档中的上限约 30 分钟。代码和文档要写进工作区才会留给下一轮。 |
| 后端切换 | 同一个面板可以连本机、Docker、虚拟机或云端，执行位置跟着后端走。 |
| 记录 | 对话、设置和自动化存在后端目录。Docker 镜像把该目录放在 `/home/openhands/.openhands`。 |

本机直接跑不需要沙箱。代理用当前用户的权限访问文件系统，适合先试通。需要把可见目录收窄时再用 Docker，只挂载项目文件夹。

**本机安装（无沙箱）**

需要 Node.js 24 或更高版本，以及 `uv`。

```powershell
npm install -g @openhands/agent-canvas
agent-canvas
```

浏览器打开 `http://localhost:8000`。确认本地后端已连接，在 Settings → LLM 配好模型，用 Open Workspace 选中仓库，再开始对话。关掉启动它的终端，本机进程会停。`agent-canvas` 没有 `--workspace` 参数，目录在面板里选。监听默认只在 `127.0.0.1`。

**Docker（只暴露指定目录）**

官方镜像的 Windows 命令写在仓库的 `README.windows.md`。macOS / Linux 的快速启动是把项目父目录挂到容器内的 `/projects`，面板在 `http://localhost:8000/canvas`：

```sh
export PROJECTS_PATH="$HOME/projects"
mkdir -p "$PROJECTS_PATH" "$HOME/.openhands"

docker run -it --rm \
  -p 127.0.0.1:8000:8000 \
  -e AGENT_CANVAS_ALLOW_LAN_SESSION_KEY=true \
  -v "$HOME/.openhands:/home/openhands/.openhands" \
  -v "${PROJECTS_PATH}:/projects" \
  ghcr.io/openhands/agent-canvas:1.28.1
```

容器里的仓库路径是 `/projects` 下的子目录。端口绑在 `127.0.0.1`，局域网其他机器访问不到。镜像标签以仓库 README 的当前版本为准。

从源码运行是克隆仓库后执行 `npm install` 和 `npm run dev`，同样打开 `http://localhost:8000`，同样没有沙箱。

## 5. 技能与流程工具

`SKILL.md` 是一个目录加一份说明：名称、何时启用、步骤、完成标准。宿主只在任务相关时读入全文。技能不自带定时器，也不授予文件权限。

| 仓库 | 约略星标 | 实际形态 | 和定时闭环的关系 |
| --- | --- | --- | --- |
| [mattpocock/skills](https://github.com/mattpocock/skills) | 29.4 万 | 一组小技能：问清需求、`tdd`、`diagnosing-bugs` | 最接近可挂进宿主的技能形状。作者明确不把整条流程包进一个技能，避免流程本身出错时难以拆开。交接文件和每小时触发要自己加。 |
| [github/spec-kit](https://github.com/github/spec-kit) | 14.2 万 | 规格驱动工具包 | 写规格、计划、实现、收敛。修 bug 和想法评估是另外的入口，不是必经阶段。产物落成规格文件。不是宿主里的一个技能槽。 |
| [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) | 10.8 万 | 工程技能集 | 含测试驱动和排错。可组合，没有闭环状态文件。 |
| [garrytan/gstack](https://github.com/garrytan/gstack) | 约 11 万 | 按角色拆的斜杠命令 | 产品、设计、工程、QA、发布。人发命令，不是定时任务。 |
| [ComposioHQ/awesome-claude-skills](https://github.com/ComposioHQ/awesome-claude-skills) | 7.7 万 | 1000 多条技能链接 | 目录。兼容 Claude Code、Codex、Cursor、Gemini CLI 等读 `SKILL.md` 的宿主。 |
| [VoltAgent/awesome-agent-skills](https://github.com/VoltAgent/awesome-agent-skills) | 3.6 万 | 官方团队与社区技能目录 | 同上，按来源整理，不是一条流水线。 |
| [VoltAgent/awesome-openclaw-skills](https://github.com/VoltAgent/awesome-openclaw-skills) | 5.3 万 | 从 ClawHub 筛过的 5300 多个 OpenClaw 技能 | 单点能力清单。清单本身过滤过垃圾和重复项。 |
| [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | — | 规格合同 | `bmad-spec` 把意图写成目录里的 `SPEC.md`，下游只读这份规格。管的是上一轮文件如何成为下一轮输入，不管定时触发。 |

另外几份体量小、专门写修 bug 步骤的技能，适合当写法参考，而不是当现成闭环：`arozumenko/sdlc-skills` 的 `bugfix-workflow`，`rmzi/portable-dev-system` 的 `bugfix`，`mgiovani/cc-arsenal` 的 `fix-bug`。共同顺序是先复现、写失败测试、再改、再跑全套验证。

OpenClaw 本体 [openclaw/openclaw](https://github.com/openclaw/openclaw) 是本地助手（当日约 35 万星），技能市场在 [openclaw/clawhub](https://github.com/openclaw/clawhub)。它说明技能可以独立发布，不说明已经有一条高星的「需求到修 bug」技能。

## 6. 和一轮接着一轮的对应关系

讨论里要的闭环是：一次触发只做一段，需求、设计、测试记录落在仓库里，下一轮只读这些文件。

| 环节 | 现成仓库给到哪一步 | 仍要自己定的 |
| --- | --- | --- |
| 谁每小时叫醒一次 | OpenHands 有定时自动化；部分宿主的定时任务可挂技能 | 电脑和客户端保持在线。云端任务读不到本机仓库。 |
| 上一轮如何交给下一轮 | OpenHands 每次新建对话。BMAD、Spec Kit 把规格写成文件。技能侧用任务卡、指针、交接快照 | 提示词必须写明先读哪份状态文件。会话记忆不会自动接上。 |
| 需求 | MetaGPT、ChatDev、Spec Kit、BMAD 强 | 未确认的需求不应直接写业务代码，否则代理会自己扩范围。 |
| 开发与命令 | OpenHands、Cline、Goose、Aider、各终端代理 | 多条定时任务打同一个工作区会抢同一份状态文件。并行要独立 worktree，不能各挂一个定时任务。 |
| 测试 | SWE-agent 和各类 `tdd` / `bugfix` 技能要求失败测试和命令证据 | 验证命令写在项目自己的技术规范里。技能套件的清单最初是空的。 |
| 界面 | 少数建议用浏览器截图 | 高星仓库没有把「无头浏览器操作 + 对照页面说明判布局缺陷」写成统一完成条件。网页可用无头方式；原生窗口截不到。 |
| 修 bug | 连续失败后应停止自修，避免一个缺陷占满后续回合 | 第 3 次仍失败就标阻塞，等人看。这不是仓库缺失，是闭环要保留的刹车。 |

没有一个高星仓库等于「一个技能挂进定时任务，就能 24 小时跑完需求、开发、测试、修 bug」。代理仓库解决运行和面板，技能仓库解决步骤和落盘格式，定时和权限在宿主里。

## 7. 选用

本机已经有能选技能、工作空间和完全访问的定时任务时，不必再套一层 OpenHands，除非需要它把 Claude Code、Codex 等多套命令行收进同一个面板，或需要容器把代理关在挂载目录里。

技能形状优先看 [mattpocock/skills](https://github.com/mattpocock/skills)：小、可改、一次做一件事。规格要落成文件时，看 Spec Kit 或 BMAD 的 `SPEC.md`，不要把整套流程产品塞进一个技能槽。修 bug 的步骤从上述三份小技能里摘顺序即可。

目录仓库只用来找单点技能。它们的星标是收录量，不是某一条交付流水线的完成度。

---

## 8. 小结

| 要点 | 结论 |
| --- | --- |
| 两条路 | 代理负责谁来干；技能负责按什么规矩干 |
| OpenHands | 最接近本机开发控制台，定时每轮是新对话 |
| 技能形状 | 小、可改、一次一件事；整条 SDLC 不要塞进一个 SKILL.md |
| 闭环缺口 | 定时、权限、状态文件交接仍在宿主和仓库约定里 |
